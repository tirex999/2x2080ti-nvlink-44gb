# 2×2080Ti + NVLink (44 GB)

Как заставить большие MoE-модели работать на двух RTX 2080 Ti с моддом на 22 ГБ.

Здесь только то, что **замерено на живом стенде**, с методикой и датами — не пересказ советов из интернета. Где вывод оказался неверным, это написано прямо, вместе с тем, что его опровергло.

## Стенд

| | |
|---|---|
| Карты | 2× RTX 2080 Ti, модд 22 ГБ каждая = **44 ГБ**, NVLink NV2, Turing sm_75 |
| Процессоры | 2× Intel Ice Lake-SP, 72 физических ядра / 144 потока |
| Память | 12 планок 32 ГБ LRDIMM 2133 (12 каналов), 377 ГБ |
| Модели | на NFS, подключены по 1 GbE |
| Контейнер | LXC, лимит памяти 140 ГБ |

Вторая нода, для сравнения по памяти: 16 планок 16 ГБ 2666 (16 каналов), 251 ГБ, карт нет.

## Два главных вывода

**Для MoE-модели, которая не влезает в видеопамять, llama.cpp — не запасной вариант, а единственный.** Только он умеет держать экспертов в оперативке, а всё остальное на картах. vLLM так не умеет, а для Qwen3.8-Flash-Next поддержки там нет вовсе: PR #53896 в апстриме открыт и не влит, в реестре форка под 2080Ti архитектура `qwen4_exp` отсутствует (проверено 30.08.2026).

**Карты решают больше, чем скорость памяти.** На одной и той же модели карты дают ×2.3, а втрое более быстрая оперативка — только ×1.44.

## Замеры

Методика везде одна: greedy (`temperature 0`), фиксированное число токенов, **обязательный прогрев**, скорости берутся из поля `timings` ответа сервера, а не секундомером. У сервера **две** разные скорости, и мерить надо обе:

- `prompt_per_second` — обработка промпта, упирается в вычисления;
- `predicted_per_second` — генерация, упирается в пропускную способность памяти.

### Qwen3.8-Flash-Next (177 B, A3B, Q4_K_M, 111 ГБ)

| конфигурация | обработка промпта | генерация |
|---|---|---|
| исходная: `-cmoe`, контекст 262144, все 144 потока | 10.5 т/с | 15.4 t/s |
| `-t 32 -tb 144` | 10.5 т/с | 16.0 t/s |
| `-ncmoe 42`, контекст 32768 | 12.0 т/с | 16.1 t/s |
| **раскладка через `-ot` по обеим картам** | **12.6 т/с** | **17.7 t/s** |
| для сравнения: на чистом процессоре, без карт | — | 6.65 t/s |

Итог настройки: генерация **+15%**, обработка промпта **+20%**.

### Одна MoE-модель на двух нодах, чистый процессор

Ornith-1.5-35B-A3B Q8_0 (35 ГБ), `llama-bench -ngl 0`, три повтора:

| | 12 каналов 2133 | 16 каналов 2666 | отношение |
|---|---|---|---|
| генерация (упор в память) | 11.95 t/s | 20.82 t/s | **1.74×** |
| обработка промпта (упор в вычисления) | 216.6 t/s | 211.9 t/s | **1.00×** |

Разделение ровно по этой линии и доказывает механизм: где считает процессор — ноды равны, где читается память — быстрая память выигрывает. Это же объясняет, почему выигрыш по полосе не переносится в скорость один к одному.

### Полоса памяти (STREAM triad, `scripts/membw.c`)

Через дробь: без закрепления потоков / с `OMP_PROC_BIND=spread OMP_PLACES=cores`.

| потоков | 12 каналов 2133 | 16 каналов 2666 |
|---|---|---|
| 32 | 76.2 / 82.4 | 255.1 / 250.7 |
| **64** | 73.8 / **84.7** | 221.3 / **268.2** |
| 96 | 68.5 / 57.8 | 251.1 / 185.6 |

Обе машины выходят на максимум на **64 потоках** и после этого падают — хотя ядер 144 и 128. Больше половины ядер полосе не помогают, а мешают. Это же видно и на самой модели: `-t 32` обыгрывает `-t 64` и `-t 96`.

Разница по полосе между нодами — 3.17×, а на живой генерации — 1.74×. Синтетика не предсказывает выход модели.

## Рабочая конфигурация

`scripts/run-next.sh` и `systemd/llama-next.service`. Ключевое:

```
-ngl 99 --load-mode mlock -fa on --numa distribute -t 32 -tb 144 -c 32768
-ot per_layer_token_embd\.weight=CPU,\
    blk\.[0-7]\.ffn_.*_exps\.weight=CUDA0,\
    blk\.[89]\.ffn_.*_exps\.weight=CUDA1,\
    blk\.1[01]\.ffn_.*_exps\.weight=CUDA1,\
    ffn_.*_exps\.weight=CPU
```

Двенадцать слоёв экспертов уезжают на карты (восемь на первую, четыре на вторую), остальные эксперты и n-грамм-таблица `per_layer_token_embd` на 28.8 ГБ остаются в оперативке. Больше двенадцати слоёв не влезает — упирается честно, в объём видеопамяти.

## Что не сработало

- **`--tensor-split` не делит буфер экспертов.** `-ncmoe` кладёт всех снятых с процессора экспертов одним буфером на одну карту; `-ts 1,1` не сдвинул раскладку ни на мегабайт. Балансировку даёт только `-ot`.
- **Урезание контекста само по себе скорости не даёт** (10.5 против 10.5 т/с). Но освобождает видеопамять, а уже она уходит под экспертов — и вот это ускоряет.
- **Кванты «под vLLM» не легче.** У Qwen3.8-Flash-Next они весят 167–175 ГБ против 111 ГБ у GGUF того же класса.

Подробности и остальные грабли — в `docs/pitfalls.md`.
