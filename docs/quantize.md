# Как самому квантовать модель из BF16

Инструкция собрана по нашим прогонам на двух RTX 2080 Ti 22 ГБ и двух Xeon Platinum 8368. Числа ниже — наши
замеры, и там, где это не замер, а арифметика, так и написано. Путь описан для GGUF и `llama.cpp`: это то, чем
модели запускаются на обычном железе, и то, что мы делаем сами.

## Коротко: что происходит

Модель на Hugging Face лежит в BF16 — по два байта на вес. Квантование заменяет эти байты на 8, 5, 4 или
меньше бит: веса группируются в блоки, и на блок запоминается один масштаб. Файл становится в два-четыре раза
меньше, и главное — больше его частей влезает в видеопамять.

Одну вещь стоит понять заранее: **разные тензоры терпят сжатие по-разному**. У модели с экспертами (MoE)
почти весь вес лежит в экспертах, а внимание и нормировки занимают единицы процентов. Поэтому экспертов режут
агрессивно, а внимание оставляют точным — так файл падает сильно, а качество почти нет. Единый тип на всю
модель (`--pure`) — худший из вариантов.

## Что понадобится

- **Место на диске: примерно три размера модели.** Исходник BF16, промежуточный GGUF BF16 и готовый квант.
  Для модели на 125 млрд параметров это 360 ГБ + 335 ГБ + сам квант; для модели на 27 млрд — 54 + 54 + 15–30 ГБ.
- **ОЗУ: не меньше того, что квантуется за один проход.** Квантование читает тензор целиком. Наш 8-битный
  прогон упирался в 189 ГиБ, и пришлось ставить планки; смешанный четырёхбитный шёл в 133 ГиБ.
- **Локальный диск, а не сетевая шара.** Квантование читает исходник подряд и быстро. У нас всё, что шло с
  гигабитной шары на вращающихся дисках, тормозило в разы: та же модель с сетевого диска поднималась 42 минуты
  вместо двух.
- **`llama.cpp`, собранный из исходников** — нужны `convert_hf_to_gguf.py` и `llama-quantize`.
- Карта для квантования не нужна вообще: это работа процессора и диска.

## Шаг 1. Забрать исходник BF16

```bash
pip install -U huggingface_hub
HF_HUB_DISABLE_XET=1 python -c "
from huggingface_hub import snapshot_download
snapshot_download('<автор>/<модель>', local_dir='./bf16-src')
"
```

Такой вызов работает в любой версии библиотеки. Консольная команда в свежих версиях называется `hf download`,
в старых — `huggingface-cli download`; если пользуетесь ею, сверьтесь со своей версией.

`HF_HUB_DISABLE_XET=1` — не косметика. Без него закачка больших репозиториев у нас обрывалась и начиналась
заново; с ним идёт ровно. Для закрытых репозиториев сначала выполните вход.

Проверьте, что скачалось целиком: число файлов и суммарный размер должны совпасть с тем, что показывает
страница модели. Недокачанный шард проявится только на шаге 2 — обидно после часа ожидания.

## Шаг 2. BF16 → GGUF

```bash
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
cmake -B build -DGGML_NATIVE=ON && cmake --build build -j --config Release
python convert_hf_to_gguf.py ../bf16-src --outtype bf16 --outfile ../model-bf16.gguf
```

Это ещё не квантование: тот же BF16, только в формате, который понимает `llama.cpp`. Шаг нужен, потому что
`llama-quantize` работает с GGUF, а не с `safetensors`.

Если конвертер падает с «unsupported architecture» — модель новее вашей копии `llama.cpp`. Обновите
репозиторий; если архитектуры нет и там, этим путём модель пока не квантуется.

## Шаг 3. Нужна ли калибровка (imatrix)

**Для 8 бит — нет.** Ошибка Q8_0 на наших прогонах выходила 0.55–0.71 % на слой и без всякой калибровки.

**Для 4 бит и ниже — да, помогает заметно.** Матрица важности показывает квантователю, какие веса влияют на
ответ сильнее, и он тратит на них точность.

```bash
./build/bin/llama-imatrix -m ../model-bf16.gguf -f calibration.txt -o ../imatrix.dat --chunks 200
```

Бинарь появляется, если сборка включала примеры; если его нет в `build/bin`, пересоберите без
`-DLLAMA_BUILD_EXAMPLES=OFF`.

В `calibration.txt` положите текст, похожий на вашу работу: будет писать код — код, отвечать по-русски —
русские тексты. Хватает нескольких мегабайт. Калибровка на чужом языке даёт модель, которая хуже отвечает
на вашем.

## Шаг 4. Само квантование: типы по тензорам

Простой вариант — один тип на всё:

```bash
./build/bin/llama-quantize ../model-bf16.gguf ../model-q8.gguf Q8_0
```

Вариант, который используем мы — разные типы разным тензорам:

```bash
./build/bin/llama-quantize \
  --imatrix ../imatrix.dat \
  --tensor-type ffn_gate_exps=iq4_nl \
  --tensor-type ffn_up_exps=iq4_nl \
  --tensor-type ffn_down_exps=iq4_nl \
  --tensor-type attn_q=q8_0 --tensor-type attn_k=q8_0 \
  --tensor-type attn_v=q8_0 --tensor-type attn_output=q8_0 \
  --token-embedding-type q8_0 \
  --output-tensor-type q8_0 \
  ../model-bf16.gguf ../model-mix.gguf Q4_K_M
```

Последний аргумент — тип по умолчанию для всего, что не названо явно. Ключ `--tensor-type` принимает
подстроку имени тензора, поэтому `attn_q` накрывает все слои сразу. Есть и `--tensor-type-file` со списком.

**Перед длинным прогоном запустите с `--dry-run`**: он покажет, какой тип получит каждый тензор, ничего не
записывая. Это пять секунд против часов, и именно здесь видны подмены типов из раздела про грабли.

Ориентир по выбору: эксперты (`ffn_*_exps`) — 4 бита и ниже, внимание (`attn_*`) — 6–8 бит, эмбеддинги и
выходной слой — 8 бит, нормировки оставить как есть. Порядок величин на нашей модели (125 млрд параметров,
512 экспертов, 10 на токен): BF16 — 335 ГБ, готовый Q4_K_M — 119 ГБ (наш замер по файлу 04.09.2026).
Переключение одного тензора `ffn_down_exps` на `iq4_nl` снимает ещё около 20 ГБ — это прямая арифметика по
формам тензоров, отдельным прогоном мы её не перемеривали.

## Шаг 5. Проверить, что получилось

Три проверки, каждая ловит свой класс ошибок.

**1. Типы в файле — те, что вы просили.** Не верьте команде, прочитайте файл:

```bash
python gguf-py/gguf/scripts/gguf_dump.py --no-tensors ../model-mix.gguf | head -40
python -c "
from collections import Counter
from gguf import GGUFReader
r = GGUFReader('../model-mix.gguf')
print(Counter(t.tensor_type.name for t in r.tensors))
"
```

Мы на этом поймали главную подмену: у модели с экспертами `ffn_down_exps` оказался не Q4_K, а Q8_0 — и файл
был заметно больше ожидаемого. Причина — в разделе про грабли.

**2. Модель отвечает.**

```bash
./build/bin/llama-cli -m ../model-mix.gguf -p "Напиши функцию на Python, считающую факториал" -n 200
```

**3. Сверка с исходником.** Задайте один и тот же вопрос исходной модели и кванту, жадно (температура 0,
фиксированный seed). Ответы не обязаны совпасть буква в букву, но смысл и структура должны. Так мы проверяли
свой 8-битный квант: три жадных ответа совпали с исходником знак в знак — это и есть доказательство, что
квантователь не испортил веса.

## Грабли, на которые мы наступили

**k-кванты требуют, чтобы ведущая размерность делилась на 256.** Самая частая и самая незаметная
неприятность. У нашей модели у тензора `ffn_down_exps` ведущая размерность 640, а 640 % 256 = 128 — и
`llama-quantize` **молча** понижает тип: Q6_K становится Q8_0, Q4_K становится Q5_0, дальше F16. Вы просили
4 бита, получили 8.5, файл вдвое больше. Лечится 32-блочными типами: 640 % 32 = 0, поэтому `iq4_nl`
(4.5 бита) законен и режет этот тензор с 42.8 до 22.7 ГБ. Проверяйте `--dry-run` и типы в готовом файле.

**Роутер MoE квантовать нельзя.** Тензор `ffn_gate_inp` стоит в жёстком исключении внутри `llama-quantize`, и
`--tensor-type` его не перебивает. Это правильно: роутер решает, каких экспертов звать, и его ошибка портит
ответ целиком. Но знайте, что он останется в F32 или BF16 и займёт своё место.

**Исходник важнее степени сжатия.** Квант из BF16 и квант из уже сжатого Q8_0 — разные вещи. Если качаете
исходник ради квантования, берите BF16, даже если он вдвое тяжелее.

**Один тип на всё — плохой выбор.** `--pure` экономит десять минут раздумий и отнимает качество там, где оно
дёшево: внимание занимает единицы процентов веса, а от сжатия страдает заметнее всего.

**Сначала посмотрите готовые кванты.** Прежде чем тратить сутки, скачайте чужой динамический квант (у unsloth,
например, точность разная по тензорам) и замерьте его на своей задаче. Если он не хуже — своего кванта не
нужно. Мы начинали именно с этой проверки.

## Когда `llama-quantize` не справится

Редкий, но реальный случай: модель с нестандартными тензорами, которые движок хочет видеть в конкретном типе.
У нас так вышло с роутерами — конвертер писал их в F32, а движок читает только BF16, и ключом это не
правилось. Тогда квантователь пишется руками на `gguf-py`: читаете исходный GGUF тензор за тензором, нужные
сжимаете (эталонная реализация Q8_0 есть в самом `ggml`), остальные копируете как есть, и пишете новый файл
потоком, не держа всё в памяти. Это сотня строк, но берётесь за это только если упёрлись: штатный путь
закрывает почти всё.

## Сколько это занимает времени

Конвертация BF16 → GGUF идёт со скоростью диска. По квантованию у нас есть замер для **своего** квантователя
на `gguf-py` (случай из предыдущего раздела): около 79 МБ/с на выходной файл, то есть 8-битный квант на 188 ГБ
считался несколько часов. Скорость `llama-quantize` на тех же данных мы отдельно не мерили — она выше, но
называть число не стану. Условие в любом случае одно: исходник на локальном диске, а не на сетевой шаре.
