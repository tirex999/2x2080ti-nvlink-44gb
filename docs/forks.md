**«Посвежее внутри ветки» не даёт ничего.** Мы мерили `v0.1.17` против

решает **смена ветки**, а не патч-релиз внутри неё.

## Как мы это запускаем

Не руками. Три слоя, и каждый нужен.

### 1. Профиль — что за модель и с какими ключами

Лежит в `profiles/<группа>/user/<имя>.env` внутри форка. Наш боевой:

```ini
SERVED_NAME=qwen38awq
QUANTIZATION=compressed-tensors
MAX_MODEL_LEN=131072
GPU_UTIL=0.94          # не 0.90: на девяноста не хватало 90 МиБ под KV при 256K
MTP_K=4                # четвёрка обыграла тройку замером
MAX_NUM_SEQS=1         # для ЧАТА; 2 роняет сервер, см. docs/pitfalls.md
LANGUAGE_MODEL_ONLY=1
SKIP_MM_PROFILING=1
DISABLE_LOG_STATS=0    # иначе нет ни скорости в журнале, ни /metrics
```

**`PROFILE` указывается путём относительно `profiles/` и целиком.** Короткое
имя молча уводит лаунчер в чужой автоподбор, и вы получите не тот конфиг,
который читаете. Проверено на своей шкуре.

### 2. Юнит systemd — чтобы пережило перезагрузку

```ini
[Unit]
StartLimitIntervalSec=3600
StartLimitBurst=6

[Service]
# Type=forking ОБЯЗАТЕЛЬНО для 0.2.x: лаунчер демонизирует сервер и выходит.
# При Type=simple systemd убивает всю группу сразу после smoke-теста.
# На 0.1.x лаунчер оставался на переднем плане, там работал Type=simple.
Type=forking
PIDFile=/root/vllm-0.2.x/run-logs/vllm-qwen38awq.pid
Environment=MODEL_DIR=/LLM/models/vllm-ready/twolven-Qwen3.8-27B-AWQ-MTP
Environment=PROFILE=qwen38awq/user/awq-k4-chat.env
Environment=MODE=normal
Environment=PORT=8000
Environment=TP_SIZE=2
Environment=ENABLE_AUTO_TOOL_CHOICE=1
Environment=TOOL_CALL_PARSER=qwen3_xml
Environment=FORCE_INCLUDE_USAGE=1
Environment=DISABLE_LOG_STATS=0
Environment=CUDA_HOME=/usr/local/cuda-13.0
ExecStart=/bin/bash /root/vllm-0.2.x/launcher.sh --non-interactive
TimeoutStartSec=1800
Restart=on-failure
RestartSec=30
KillMode=mixed
```

Готовый файл — [`../vllm/qwen38-02x-production/`](../vllm/qwen38-02x-production/).

### 3. Переменные окружения бьют всё остальное

Это не мелочь, а способ управлять лаунчером снаружи. В нём есть
`register_env_config_overrides`: экспортированная переменная с именем
известного ключа становится переопределением с источником `env`, и оно
**сильнее и профиля, и файла состояния** `run-logs/start-manager.state`.

Мы на этом попались: правка `DISABLE_LOG_STATS=0` в профиле не подействовала —
значение перезаписывалось из файла состояния при каждом старте. Снялось
только переменной окружения в юните.

## Проверить свою машину перед сборкой

```bash
bash scripts/check-prereqs.sh
```

Ничего не меняет. Смотрит систему, ядро, GCC, glibc, CUDA, драйвер, архитектуру
карт — и говорит, соберётся ли `0.2.x`, а если нет, то что именно мешает.
