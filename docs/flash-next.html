Qwen3.8-Flash-Next на 2×2080Ti — наш рецепт

Официальный рецепт vLLM для этой модели начинается с 4×H100 и требует, чтобы вся модель лежала в видеопамяти: чекпоинт в FP8 весит 172 ГБ, в BF16 — 335 ГБ. У нас 44 ГБ видеопамяти на двух картах. Поэтому ниже — не адаптация чужого рецепта, а свой, собранный на живом стенде.

Всё, что здесь написано, измерено. Где числа — это наши замеры, не документация.

Почему FreeToken, а не vLLM и не llama.cpp

Ключ ко всему — где считаются эксперты. У модели 125 млрд параметров, из них 120.8 млрд — роутируемые эксперты, и на каждый токен работают только 10 из 512.

движок эксперты подходит нам
vLLM только в VRAM (в host RAM выносится лишь n-граммная таблица) нет: 172 ГБ против наших 44
llama.cpp в RAM, но без перекрытия — две цепочки идут по очереди хуже
FreeToken --moe-backend cpu: считает на AVX-512 VNNI, перекрывая с картой да

У FreeToken вся последовательность захвачена в CUDA-граф: выгрузка скрытых состояний на хост → host-функция ставит задачу в пул потоков → ожидание → возврат выхода экспертов на карту. Это ровно наша конфигурация: плотная часть на карте, эксперты на процессоре.

Железо, на котором это работает

  • 2× RTX 2080Ti, модифицированные до 22 ГБ каждая (Turing, sm_75), NVLink NV2
  • обе карты на PCIe Gen3 x16 — проверять под нагрузкой, в простое NVIDIA штатно роняет линк до Gen1
  • два сокета, 128 потоков, AVX-512 VNNI
  • 16 планок DDR4-2666, все каналы заполнены
  • 251 ГБ ОЗУ хоста, контейнеру отдано 205 ГБ

Модель: RadixArk/Qwen3.8-Flash-Next-NVFP4, 126 ГБ, лежит локально (/root/models/flash-next-nvfp4). По сети с NFS-шары она грузится минутами — это была отдельная потерянная ночь.

Установка

Сборки нет — это питоновский пакет, ставится в отдельный venv:

uv pip install "freetoken[accel]"      # venv: /root/ft-venv

Требуется: Linux x86_64, драйвер r580+, CUDA 13 с nvcc в работе (ядра компилируются при первом использовании), Python ≥3.10. Образ обязан остаться devel — ужать до runtime нельзя. Нужен том под кеш ядер, иначе каждый запуск компилирует заново и первые замеры врут.

Рабочая команда

export CUDA_VISIBLE_DEVICES=1          # одна карта; TP для этой модели не поддержан, см. ниже
export FT_CPU_PREFILL=256              # наша врезка: префилл на AVX-512
export TRITON_CACHE_DIR=/root/.triton/cache-ft

exec numactl --interleave=all /root/ft-venv/bin/ft serve \
  --model /root/models/flash-next-nvfp4 \
  --host 0.0.0.0 --port 1919 \
  --moe-backend cpu \
  --moe-cpu-threads 64 \
  --attention-backend auto \
  --ple-backend pinned \
  --memory-ratio 0.85 \
  --max-running-requests 1 \
  --max-prefill-length 262144 \
  --max-output-tokens 262144

Что делает каждый флаг, который не очевиден:

  • numactl --interleave=all — чередование по обоим узлам, +8% против одного узла.
  • --moe-cpu-threads 64 — 32 потока уже насыщают один узел, 128 проверены и не оправдались.
  • --ple-backend pinned — таблица n-грамм (47.7 ГБ) закрепляется в хостовой памяти. Умолчание disk читает её из файлов чекпоинта, и на сетевой шаре это смерть.
  • --max-running-requests 1 — намеренно. Батч из двух с MTP и CUDA-графом ронял движок. Следствие: пока идёт один запрос, остальные ждут — это очередь, а не поломка.
  • FT_CPU_PREFILL=256 — врезка, дала префиллу 127×. Обновление пакета её снесёт, см. грабли.

Про полосу памяти: не объяснять ею скорость

Это ловушка, в которую легко попасть дважды.

раскладка полоса, ГБ/с
14 планок, один узел 76.8
14 планок, оба узла 122.8
16 планок, один узел 137.8
16 планок, оба узла 175.7

Заполнение двух пустых каналов подняло полосу на 43%, а скорость модели — на 7% (19.5 → 20.9 т/с). Тот же вывод независимо получен 30.08 сравнением двух нод: разница в полосе 2.78 раза, разница в токенах — 9.6%.

Вывод, который надо держать в голове: полоса памяти — не главный ограничитель. Улучшать её стоит (она дешева и работает в плюс), но обещать по ней прирост нельзя.

Что на самом деле ограничивает

Профиль вычислений (ft bench bw --dtype nvfp4):

CPU STREAM read 192.0  |  PCIe H2D 10.2  D2H 11.3  GB/s
nvfp4   CPU-MoE 78.4 GB/s   PCIe-gather 10.2 GB/s   = 7.65x   → hybrid

Процессор быстрее шины в 6–7.6 раза даже на исправной x16 — отсюда выбор --moe-backend cpu и отсюда же то, что починка линий x1 → x16 почти не сдвинула скорость этой модели.

Замер загрузки карты во время генерации: занята 41%, пик 52%, 158 Вт из 250. Больше половины шага она ждёт. Раскладка шага при 51 мс (19.5 т/с): чтение плотной части с карты ~10 мс, чтение активных экспертов из ОЗУ ~11 мс, остальные ~30 мс — синхронизации, host-функции CUDA-графа, PLE, роутинг.

То есть узкое место — не карта, не шина и не полоса памяти, а число проходов и накладные внутри шага. Отсюда следует, куда бить дальше.

Что проверено и отвергнуто

Это самая ценная часть: каждый пункт стоил времени.

  • --moe-backend hybrid — 6.9–8.4 т/с против 19.5 на cpu, втрое хуже. Профилировщик движка сам его рекомендует — не верить: подкачка по шине отъедает ту же полосу DRAM, которой пользуется CPU-MoE. Проверено дважды, в том числе на целой шине.
  • Эксперты в VRAM — вдвое хуже процессорных. Пустая карта тут не рычаг.
  • Тензорный параллелизм TP=2 — не поддержан: qwen4_exp weight loading supports TP=1 only (models/qwen4_exp/weight.py:161). И это не забытая мелочь: TP=1-only у всех гибридных моделей дерева (qwen3_5_moe, glm5_next, muse_glimmer, minimax_m3), модель написана на реплицированных линейках. Плюс при TP=2 каждый ранг дублирует PLE 47.7 ГБ и банки экспертов.
  • 128 потоков — не оправдались против 64.
  • Сжатие KV в fp8 — не рассматриваем по решению архитектора.

Грабли

Обновление пакета сносит врезки. FT_CPU_PREFILL живёт двумя правками внутри venv (engine/engine.py и layers/moe.py). После обновления пакета их нет, а скорость падает молча. Держать форк: /root/ft-fork.

Падение по видеопамяти на длинном ответе. Раскладка при старте:

Free memory before loading model: 21.32 GiB
Allocating 205504 tokens for KV cache, K + V = 4.85 GiB
Free memory after initialization: 3.20 GiB

Модель с буферами берёт 13.3 ГБ, KV — 4.85 ГБ, свободными остаются 3 ГБ. В них живут рабочие буферы внимания, которые растут с длиной. На ответе, где контекст дорос до 31 тысячи токенов, они кончились:

torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 162.00 MiB ... 10.19 MiB free
Backend worker is gone and cannot be restarted; stopping the API server

Важно: воркер умирает, и сервер гасит сам себя. Снаружи это выглядит как «модель пропала». KV тут ни при чём — он рассчитан на 205 тысяч токенов, контекст в него влезал.

Модель по умолчанию думает на максимуме. /v1/models отдаёт default_reasoning_effort: xhigh. Размышление доходит до десятков тысяч токенов, и ответ идёт двадцать минут. Усилие задаётся в запросе (reasoning_effort), флага у сервера нет.

Скорость генерации ≠ время ответа. Полное время = префилл + размышление + ответ. Префилл идёт около 100 т/с, то есть файл на 13 тысяч токенов — это две минуты до первого символа. На коротком вопросе незаметно, на разборе файла решает всё.

Оборванный поток не отменяет запрос. Если чат потерял соединение, движок продолжает генерировать в никуда, а ответ не доходит до базы. Занятость проверять по журналу: journalctl -u ftserve | grep "gen throughput".

pkill -f "ft serve" убивает собственную оболочку — строка команды содержит тот же текст. Писать pkill -f "[f]t serve".

Обслуживание

Подъём (transient-юнит, переживает выход из сессии):

pct exec 110 -- systemd-run --unit=ftserve --setenv=HOME=/root /bin/bash /root/ft_cpu.sh

Проверять живость пробой, а не статусом — сервер поднимается две минуты:

curl -s -m 8 -X POST http://192.168.1.175:1919/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"flash-next-nvfp4","messages":[{"role":"user","content":"hi"}],"max_tokens":1}'

В Open WebUI (0.10.2) подключение живёт в базе webui.db плоскими ключами openai.api_base_urls / openai.api_keys / openai.api_configs / openai.enable. Живая база — та, что смонтирована в контейнер (docker inspect open-webui), а не первая найденная поиском. Перед правкой контейнер останавливать — иначе пишешь в базу с WAL.

Что дальше

Раз ограничивает число проходов и накладные внутри шага, бить надо туда:

  1. Спекуляция MTP. Голова написана и грузится (форк, коммит a9c7e5f), не хватает цикла «черновик → проверка → принятие». Штатной спекуляции в FreeToken нет вовсе. Проверка нескольких токенов стоит почти как генерация одного — здесь счёт идёт на разы, а не проценты.
  2. 12 слоёв полного внимания на вторую карту. Она простаивает, а падаем мы по её соседке. Освобождает 4.85 ГБ там, где не хватило 162 МБ. Резать надо по границе слоя, а не переносом пула: ядро внимания получает q/k/v с одной карты и K/V из пула — с разных карт Triton не запускается. Состояние 36 GDN-слоёв переносить нельзя, оно в горячем пути.
