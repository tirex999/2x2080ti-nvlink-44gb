Вторая карта — сопроцессор слоя (STRATA_HELPER)

Раньше главная карта считала каждый слой целиком, а вторая только помогала экспертами, причём работу ей на каждом слое ставил хост вызовами API. Теперь у каждой карты свой CUDA-граф окна проверки; карты встречаются на флагах в своей памяти, вторая сама забирает вход слоя по NVLink и пишет результат прямо в буферы главной:

Процессоры: NVFP4 на AVX-512 и расписание пула

ggml-cpu считает NVFP4 × Q8_0 на x86 только AVX2 и на каждый токен окна заново распаковывает строку весов. src/kernels/cpu/nvfp4_avx512.cpp: строка распаковывается один раз на все токены, каждый токен — один VPDPBUSD на блок, а плавающая часть повторяет ядро ggml операция в операцию, поэтому результат побитно тот же (0 расхождений из 13 608). Одно ядро процессора: ×1.3 на одном токене, ×1.9 / ×2.5 / ×2.7 на 2 / 3 / 4 токенах. В движке пул 5.1 → 4.7 мс на раунд. Микробенчмарк пула (pool_bench: один слой, 3 эксперта, 63 потока на двух сокетах): 58 → 51 мкс; статическое расписание строк вместо захвата задач атомиками — ещё до 35 мкс, но в живом движке выигрыша нет, разбираемся.

Эксперты Q8_0 из официального FP8

Q8_0 — 8.5 бита на вес, эксперт весит 5.2 МБ против 2.76 МБ у NVFP4, все эксперты — 128 ГБ. Конвертер tools/q8_experts.py берёт FP8-чекпойнт Qwen (float8_e4m3fn, масштаб на блок 128×128), восстанавливает веса и квантует их по правилу ggml. Ядра для карты — порт vec_dot_q8_0_q8_1 из llama.cpp; процессор считает их через ggml-cpu. Сверка ядер: карта и процессор совпадают до 1e-7.

Сеть: 1 Гбит/с между узлами

Физические сетевые карты узлов — 1 Гбит/с (мост Proxmox показывает 10G, но это виртуальная цифра). Поэтому NFS упирается в ~115 МБ/с: эксперты NVFP4 (68 ГБ) грузятся ~10 минут, Q8_0 (128 ГБ) — ~20 минут, конвертация FP8 → Q8_0 заняла 32 минуты. Ночное резервное копирование Proxmox (с 01:00, архивы на то же NFS) забирает канал целиком: загрузка модели падает до ~12 МБ/с, а ядро со сжатием мешает крутящемуся пулу Strata — замеры в это время не ставим.

Что дальше

  • Одному запросу NVLink даст больше всего, если делить каждый слой пополам между картами: 34 мс работы главной карты по прикидке превратятся в ~17 мс на каждой плюс суммирование по NVLink (не мерено).

Новое 27.09, ночь: Strata отвечала жадно — теперь выборка, как у FreeToken

На FreeToken с NVFP4 сцены выходят умнее, чем на Strata с нашим квантом. Сверка по весам этого не объясняет. Плотная часть кванта A бит в бит совпадает с Q8_0 из BF16-чекпоинта NVIDIA. Эксперты IQ4_XS/IQ4_NL ближе к официальному FP8, чем NVFP4: ошибка 8.5 % против 9.8 % на 18 матрицах. Разница нашлась в самом движке, в трёх местах.

  1. Strata отвечала жадно на любой запрос. Сервер не читал из запроса temperature, top_p и top_k. Окно проверки черновиков было жёстко на argmax. А модель рассчитана на выборку: в её generation_config.json стоит do_sample: true, и в заметках NVIDIA к чекпоинту рекомендованная выборка — temperature 1.0, top_p 0.95, top_k 20. Ядро выборки у автора есть, но оно считает один токен одним потоком и тратит 5–6.5 с на вызов. Видимо, поэтому в окне и стоял argmax.
  2. Порядок фильтров. В Strata цепочка llama.cpp: top_p считается по сырым логитам, температура применяется после. FreeToken (flashinfer), vLLM и HF сначала делят логиты на температуру, потом режут top_k и top_p. Так эти параметры понимает любой OpenAI-совместимый сервер. При T < 1 порядок llama.cpp оставляет в выборке лишние хвостовые токены.
  3. KV в int8. Мы запускали с --kv int8. У автора это экспериментальный режим: по умолчанию fp16, пока его проверка G-C не приняла int8. На размышлениях в 40 тысяч токенов и больше такое может сказываться на коде.

Что сделано:

  • Ядро выборки «блок на токен». Каждый из 256 потоков держит свой отсортированный top-K и читает логиты по 8 за раз. Затем K раундов выбора лучшего по всему блоку. Конец (top_p, температура, softmax, розыгрыш Philox) — код эталона без изменений. Сверка с эталоном на настоящем словаре (248 320 токенов, с точными ничьими на вершине): 0 расхождений в 672 выборах (два прогона сверки). Эталон тратит 6.5 с на вызов, новое ядро — 1.1 мс на окно из 5 строк (замер событиями GPU). Это около 3 % раунда; жадное ядро — 48 мкс, так что тут есть что ускорять.
  • Выборка в графе окна проверки. Пара «счётчик, зерно» лежит в отображённой памяти, и граф при каждом запуске берёт новые числа. Черновик MTP принимается, только если совпал с разыгранным токеном. Это точная спекулятивная выборка. Равномерное число для розыгрыша зависит только от зерна и позиции, поэтому при том же зерне ответ совпадает с выборкой без черновиков токен в токен.
  • Сервер передаёт движку параметры запроса. temperature, top_k, top_p и seed идут из запроса, по умолчанию 0.6 / 20 / 0.95. Порядок фильтров — как у vLLM; STRATA_SAMPLE_ORDER=llama возвращает прежний. Для прямого запуска есть ключи --seed, --temperature, --top-k, --top-p и --temp-first.
  • Точность KV задаётся при запуске. В strata_run_fast.sh появился ключ KV=fp16|int8.

Новое 27.09, вечер: оба сокета и таблица n-грамм в памяти — до 74 т/с

На графике Proxmox было видно: пока работает Strata, процессор двое суток держится ровно на 50 %, а нагружена одна карта. Замер нашёл две причины, обе в движке.

  1. Пул процессора сидел не там. В physical_cores() висячий else: каждый процессор вне маски добавлял в список всю машину, и список начинался с 0, 1, 2… Половина рабочих (31 из 63) и поток хоста садились на сокет 0, а все 61 ГиБ экспертов под numactl --membind=1 лежали в памяти сокета 1 и читались через межсокетную шину. 50 % на графике — это 64 потока, по одному на физическое ядро, крутящихся в ожидании работы.
  2. Таблица n-грамм уходила на диск. Арену экспертов движок читает из GGUF через кэш ОС, и эти 61 ГиБ выдавливали из памяти таблицу n-грамм: из 50.7 ГиБ оставалось 10.8. Строки таблицы для каждого токена читались с диска — 30 мс из 72 мс раунда. Этим же объясняется, почему 8-битная таблица NVIDIA шла медленнее 4.5-битной.

Что сделано (ключ --numa, уже в патче):

  • арена раскладывается по узлам: половина строк каждого эксперта (gate/up и down) в памяти узла 0, половина — узла 1 (30.6 и 30.4 ГиБ). Каждый сокет считает свои строки из своей памяти, потом добирает чужие; поток хоста и его память — на узле главной карты;
  • GGUF выгружается из кэша по ходу загрузки, таблица после арены прогревается и закрепляется в памяти (mlock);
  • рабочие пула без работы через 50 мс засыпают: сервер без запросов больше не держит 64 ядра.

У 2080Ti шина 3.0, процессор считает эксперта примерно в 3.5 раза быстрее, чем шина его привозит. С одной картой лучшее — 0.15, с двумя — 0, и тогда ядра этого пути выкидываются из графа.
  • Таблица n-грамм — из памяти. На Linux движок читал её с диска по одной строке (pread с O_DIRECT, асинхронное чтение не доделано) — 7–10 % времени. Режим --ple-io mmap и прогрев файла в кэш ОС убрали это.
  • Свои ядра гипер-связей. Штатные занимали 41 блок на 68 мультипроцессоров карты; разложенные на всю карту, они совпадают со штатными до округления fp32 и экономят ~2 мс на раунд.
  • Раскладка экспертов снята на чужих промптах. Какие эксперты класть на какую карту, решает таблица частот маршрутизации. Мы сняли её на шести других задачах (не на хомяках и не на аквариуме) и проверили: стоимость раунда та же, что у раскладки, подогнанной под тест. То есть цифры выше — не подгонка.
  • Перенос на Linux: пул рабочих процессора ставил по два потока на физическое ядро (сиблинги SMT) — исправлено.

Проверено и отвергнуто: огромные страницы для арены экспертов (без изменений), окно черновика 6 токенов вместо 4 (хуже: 47.9 против 60.5 т/с), запуск графа отдельным потоком (−0.8 %), эксперты сразу на обеих картах с делением на лету (+2.5 % при росте промахов — не стоит того), другие раскладки плотных проекций (без разницы).

Оговорки:

  • Скорость сильно зависит от того, как угадывает черновик. Хомяки и аквариум — это код, его легко предсказать: 2.1–3.5 токена за проход. На разговорных текстах черновик угадывает хуже, и выходит 45–55 т/с.
  • Один запрос за раз, кэш между запросами не переиспользуется: каждый ход перечитывает весь контекст.
  • Второй процессор не понадобился: когда промахи ушли на вторую карту, считать процессору почти нечего.
  • Первая съёмка кадров у прогонов на двух картах вышла пустой — в тот момент не открылся CDN с three.js («THREE is not defined»). Страницы исправны, кадры пересняты.

Почему FreeToken, а не vLLM и не llama.cpp

Ключ ко всему — где считаются эксперты. У модели 125 млрд параметров, из них 120.8 млрд — роутируемые эксперты, и на каждый токен работают только 10 из 512.

движок эксперты подходит нам
vLLM только в VRAM (в host RAM выносится лишь n-граммная таблица) нет: 172 ГБ против наших 44
llama.cpp в RAM, но без перекрытия — две цепочки идут по очереди хуже (до 26.09; с PR #27861 и кэшем экспертов — лучший результат, см. раздел выше)
FreeToken --moe-backend cpu: считает на AVX-512 VNNI, перекрывая с картой да

У FreeToken вся последовательность захвачена в CUDA-граф: выгрузка скрытых состояний на хост → host-функция ставит задачу в пул потоков → ожидание → возврат выхода экспертов на карту. Это ровно наша конфигурация: плотная часть на карте, эксперты на процессоре.

Железо, на котором это работает

  • 2× RTX 2080Ti, модифицированные до 22 ГБ каждая (Turing, sm_75), NVLink NV2
  • обе карты на PCIe Gen3 x16 — проверять под нагрузкой, в простое NVIDIA штатно роняет линк до Gen1
  • два сокета, 128 потоков, AVX-512 VNNI
  • 16 планок DDR4-2666, все каналы заполнены
  • 251 ГБ ОЗУ хоста, контейнеру отдано 205 ГБ

Модель: RadixArk/Qwen3.8-Flash-Next-NVFP4, 126 ГБ, лежит локально (/root/models/flash-next-nvfp4). По сети с NFS-шары она грузится минутами — это была отдельная потерянная ночь.

Установка

Сборки нет — это питоновский пакет, ставится в отдельный venv:

Требуется: Linux x86_64, драйвер r580+, CUDA 13 с nvcc в работе (ядра компилируются при первом использовании), Python ≥3.10. Образ обязан остаться devel — ужать до runtime нельзя. Нужен том под кеш ядер, иначе каждый запуск компилирует заново и первые замеры врут.

Рабочая команда

export FT_CPU_PREFILL=256              # наша врезка: префилл на AVX-512

exec numactl --interleave=all /root/ft-venv/bin/ft serve \
  --model /root/models/flash-next-nvfp4 \
  --host 0.0.0.0 --port 1919 \
  --moe-backend cpu \
  --moe-cpu-threads 64 \
  --attention-backend auto \
  --ple-backend pinned \
  --memory-ratio 0.85 \
  --max-running-requests 1 \

Что делает каждый флаг, который не очевиден:

  • numactl --interleave=all — чередование по обоим узлам, +8% против одного узла.
  • --moe-cpu-threads 64 — 32 потока уже насыщают один узел, 128 проверены и не оправдались.
  • --ple-backend pinned — таблица n-грамм (47.7 ГБ) закрепляется в хостовой памяти. Умолчание disk читает её из файлов чекпоинта, и на сетевой шаре это смерть.
  • --max-running-requests 1 — намеренно. Батч из двух с MTP и CUDA-графом ронял движок. Следствие: пока идёт один запрос, остальные ждут — это очередь, а не поломка.
  • FT_CPU_PREFILL=256 — врезка, дала префиллу 127×. Обновление пакета её снесёт, см. грабли.

Что на самом деле ограничивает

Профиль вычислений (ft bench bw --dtype nvfp4):

Процессор быстрее шины в 6–7.6 раза даже на исправной x16 — отсюда выбор --moe-backend cpu и отсюда же то, что починка линий x1 → x16 почти не сдвинула скорость этой модели.

Замер загрузки карты во время генерации: занята 41%, пик 52%, 158 Вт из 250. Больше половины шага она ждёт. Раскладка шага при 51 мс (19.5 т/с): чтение плотной части с карты ~10 мс, чтение активных экспертов из ОЗУ ~11 мс, остальные ~30 мс — синхронизации, host-функции CUDA-графа, PLE, роутинг.

То есть узкое место — не карта, не шина и не полоса памяти, а число проходов и накладные внутри шага. Отсюда следует, куда бить дальше.

Что проверено и отвергнуто

Это самая ценная часть: каждый пункт стоил времени.

  • --moe-backend hybrid — 6.9–8.4 т/с против 19.5 на cpu, втрое хуже. Профилировщик движка сам его рекомендует — не верить: подкачка по шине отъедает ту же полосу DRAM, которой пользуется CPU-MoE. Проверено дважды, в том числе на целой шине.
  • Эксперты в VRAM — вдвое хуже процессорных. Пустая карта тут не рычаг.
  • Тензорный параллелизм TP=2 — не поддержан: qwen4_exp weight loading supports TP=1 only (models/qwen4_exp/weight.py:161). И это не забытая мелочь: TP=1-only у всех гибридных моделей дерева (qwen3_5_moe, glm5_next, muse_glimmer, minimax_m3), модель написана на реплицированных линейках. Плюс при TP=2 каждый ранг дублирует PLE 47.7 ГБ и банки экспертов.
  • 128 потоков — не оправдались против 64.
  • Сжатие KV в fp8 — не рассматриваем по решению архитектора.

Чат через Open WebUI: бюджет вывода и потеря ответов

Разобрано 09.09.2026 по симптому «задаю вопрос — ответ не приходит, в истории пусто». Три независимые причины, каждая подтверждена замером.

1. Бюджет вывода 32768 вместо заданного флагом. Open WebUI не присылает max_tokens. FreeToken в этом случае берёт зашитую константу:

# freetoken/server/generation.py
DEFAULT_MAX_OUTPUT_TOKENS = 32768
max_tokens = DEFAULT_MAX_OUTPUT_TOKENS if max_tokens is None else max_tokens

Флаг --max-output-tokens читается только в Responses API (responses_api.py:153), а OpenAI-ручка — та, которой пользуются Open WebUI и большинство клиентов — его игнорирует. То есть флаг стоит, а работает вхолостую. Нам это стоило пустых ответов: на задаче «3D-сцена одним файлом» модель тратит около 29000 токенов только на планирование, и при бюджете 32768 на сам код оставалось менее 4000 — ответ физически не помещался.

Врезка в форк (generation.py + openai_api.py) приводит OpenAI-ручку к поведению Responses API: resolve_sampling принимает default_max_tokens, а handle_chat_completion передаёт в него state.config.max_output_tokens. Без параметра поведение прежнее.

2. Ответ не сохраняется, если клиент отвалился. Open WebUI 0.10.2 при ENABLE_REALTIME_CHAT_SAVE=False (это дефолт, env.py:360) пишет ответ в базу одним куском в самом конце (utils/middleware.py:5226). Ответ, который идёт двадцать минут, переживает обрыв браузера только при ENABLE_REALTIME_CHAT_SAVE=true — тогда запись идёт по мере генерации. Симптом выключенного режима узнаваем: в chat_message строка user записана целиком, а assistant — ровно 2 знака, с временем создания на секунду позже вопроса.

Замер, который это доказал: движок принял запрос в 06:34:00, дошёл до 38900 токенов контекста к 07:00:12, ушёл в Scheduler is idle — и ни одного 200 OK в журнале. Ответ дописан в оборванный сокет.

3. Фоновые вызовы воруют единственный слот. На каждое сообщение Open WebUI дополнительно зовёт модель за заголовком чата, тегами и подсказками-продолжениями. При --max-running-requests 1 они встают в ту же очередь, что и настоящий ответ. В журнале это выглядит обманчиво: 200 OK есть, а ответа в чате нет — потому что 200 OK принадлежал заголовку. Выключать task.tags.enable и task.follow_up.enable; заголовок можно оставить, он короткий (префилл около 30 токенов).

Настройки Open WebUI живут в таблице config базы webui.db — она плоская, key/value:

update config set value = 'false' where key = 'task.tags.enable';
update config set value = 'false' where key = 'task.follow_up.enable';
update config set value = '{"max_tokens": 262144}' where key = 'models.default_params';

models.default_params применяется ко всем моделям (main.py:1044), в том числе к тем, у которых нет своей записи в таблице model — а у подключённой напрямую модели её нет. Читается из базы на каждый запрос, перезапуск контейнера для него не нужен; переменные окружения вроде ENABLE_REALTIME_CHAT_SAVE — нужен.

"env": {

  "ANTHROPIC_AUTH_TOKEN": "freetoken",

  "ANTHROPIC_DEFAULT_SONNET_MODEL": "flash-next-nvfp4",

Скорость генерации прямо в чате

Open WebUI 0.10.2 скорость не считает — ни фронтенд, ни бэкенд. Он умеет вычислять её только для Ollama-подключений (utils/response.py:170-184, поле response_token/s из eval_count и eval_duration); для OpenAI-совместимых серверов этот код не вызывается, а поиск по исходникам всей сборки не даёт ни одного совпадения на token/s. Значит цифру должен прислать сам сервер.

Дверь для этого есть, и правок Open WebUI она не требует — utils/middleware.py:4152:

raw_usage.update(data.get('timings', {}))  # llama.cpp

Любой объект timings на верхнем уровне финального чанка вливается прямо в usage. Дальше normalize_usage (result = dict(usage)) сохраняет все исходные поля, а merge_usage складывает только токены и стоимость — остальное «keeps the latest provider value». Показывается это в подсказке у иконки «i» под ответом (ResponseMessage.svelte:1160); отдельной строки со скоростью в 0.10.2 не существует.

Нужны оба шага, порознь не работают.

Шаг 1 — включить у модели способность «Usage». Без неё фронтенд не добавляет в запрос stream_options: {include_usage: true} (Chat.svelte:2604-2607), и сервер не присылает ничего. Для модели, подключённой напрямую (своей строки в таблице model нет), действует глобальный ключ:

-- в capabilities добавить "usage": true
select value from config where key = 'models.default_metadata';

Читается из базы при формировании списка моделей (utils/models.py:295) — перезапуск контейнера не нужен, достаточно обновить страницу.

Шаг 2 — врезка в движок (server/openai_api.py): в stream_chat_completion_chunks засекается начало запроса и момент первого события, а в финальный чанк рядом с usage кладётся timings. Скорость ответа считается по времени генерации, а не по всему запросу: иначе долгий префилл на процессоре занижал бы её втрое и цифра расходилась бы с той, что движок печатает в журнал (gen throughput (token/s)).

Что приходит после обоих шагов (живая проба):

"usage":   {"prompt_tokens": 65, "completion_tokens": 39, "total_tokens": 104},
"timings": {"time_to_first_token_s": 0.83, "generation_time_s": 1.86,
            "total_time_s": 2.69, "response_token/s": 20.91, "prompt_token/s": 78.71}

Имена полей взяты в стиле Ollama-пути Open WebUI, чтобы подсказка читалась одинаково для любой модели.

На vLLM это делается штатно

У vLLM свой счётчик уже есть, писать ничего не надо — достаточно флага --enable-per-request-metrics. Он кладёт в финальный чанк стрима объект metrics:

"metrics": {"time_to_first_token_ms": 83.65, "generation_time_ms": 1602.0,
            "queue_time_ms": 0.008, "mean_itl_ms": 14.97, "tokens_per_second": 64.07}

Флаг требует включённой статистики движка: вместе с --disable-log-stats vLLM откажется стартовать (cli_args.py, проверка при разборе аргументов).

Мостик всё равно нужен: Open WebUI читает только верхнеуровневый timings и поле metrics не смотрит. Поэтому рядом кладутся те же числа в секундах под именами, которые интерфейс уже понимает. Правка протокола не требуется — ChatCompletionStreamResponse наследует OpenAIBaseModel с ConfigDict(extra="allow"), поэтому лишнее поле проходит.

Такой источник цифры лучше самодельного: скорость считает сам движок, и это видно в ответе рядом с нашими полями — удобно, когда числа нужно кому-то показать.

Про лимит вывода при этом: на vLLM max_tokens во весь контекст ставить НЕЛЬЗЯ. Он требует prompt_tokens + max_tokens <= max_model_len и отвергает запрос с текстом «you requested N output tokens and your prompt contains ...». Параметр в Open WebUI надо просто не задавать — тогда под ответ уходит весь остаток контекста. FreeToken в той же ситуации избыточное значение молча урезает, поэтому настройка, вылеченная на одном движке, на другом становится поломкой: при смене движка параметры по умолчанию пересматривать.

Грабли

Обновление пакета сносит врезки. FT_CPU_PREFILL живёт двумя правками внутри venv (engine/engine.py и layers/moe.py). После обновления пакета их нет, а скорость падает молча. Держать форк: /root/ft-fork.

Падение по видеопамяти на длинном ответе. Раскладка при старте:

Free memory before loading model: 21.32 GiB
Allocating 205504 tokens for KV cache, K + V = 4.85 GiB
Free memory after initialization: 3.20 GiB

Модель с буферами берёт 13.3 ГБ, KV — 4.85 ГБ, свободными остаются 3 ГБ. В них живут рабочие буферы внимания, которые растут с длиной. На ответе, где контекст дорос до 31 тысячи токенов, они кончились:

torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 162.00 MiB ... 10.19 MiB free
Backend worker is gone and cannot be restarted; stopping the API server

Важно: воркер умирает, и сервер гасит сам себя. Снаружи это выглядит как «модель пропала». KV тут ни при чём — он рассчитан на 205 тысяч токенов, контекст в него влезал.

Модель по умолчанию думает на максимуме. /v1/models отдаёт default_reasoning_effort: xhigh. Размышление доходит до десятков тысяч токенов, и ответ идёт двадцать минут. Усилие задаётся в запросе (reasoning_effort), флага у сервера нет.

Скорость генерации ≠ время ответа. Полное время = префилл + размышление + ответ. Префилл идёт около 100 т/с, то есть файл на 13 тысяч токенов — это две минуты до первого символа. На коротком вопросе незаметно, на разборе файла решает всё.

Оборванный поток не отменяет запрос. Если чат потерял соединение, движок продолжает генерировать в никуда, а ответ не доходит до базы. Занятость проверять по журналу: journalctl -u ftserve | grep "gen throughput".

pkill -f "ft serve" убивает собственную оболочку — строка команды содержит тот же текст. Писать pkill -f "[f]t serve".

docker-compose 1.29.2 на Docker 28 разрушает контейнер. docker-compose up -d падает с KeyError: 'ContainerConfig', но ДО падения успевает переименовать и остановить старый контейнер — сервис лежит, а новый не создан. Плагина docker compose v2 в контейнере нет. Поднимать напрямую docker run с набором из compose-файла; тома именованные, данные переживают пересоздание, .webui_secret_key лежит в томе, поэтому разлогина не происходит.

Правка в форке не действует, пока не перенесена в рабочую копию. Служба запускается из /root/ft-venv/lib/python3.10/site-packages/freetoken — это отдельная копия дерева, а не ссылка на форк. Порядок всегда один: правка в форк, cp в site-packages, перезапуск.

Что дальше

Раз ограничивает число проходов и накладные внутри шага, бить надо туда:

  1. Спекуляция MTP. Голова написана и грузится (форк, коммит a9c7e5f), не хватает цикла «черновик → проверка → принятие». Штатной спекуляции в FreeToken нет вовсе. Проверка нескольких токенов стоит почти как генерация одного — здесь счёт идёт на разы, а не проценты.
  2. 12 слоёв полного внимания на вторую карту. Она простаивает, а падаем мы по её соседке. Освобождает 4.85 ГБ там, где не хватило 162 МБ. Резать надо по границе слоя, а не переносом пула: ядро внимания получает q/k/v с одной карты и K/V из пула — с разных карт Triton не запускается. Состояние 36 GDN-слоёв переносить нельзя, оно в горячем пути.
