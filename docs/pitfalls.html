Грабли

Всё ниже оплачено временем на живом стенде, а не вычитано.

llama.cpp

-ot нельзя писать несколько раз. Сервер берёт только последнее правило и пишет в журнал:

DEPRECATED: argument '-ot' specified multiple times,
            use comma-separated values instead (only last value will be used)

Все правила — одним флагом через запятую. Проверка честности: в журнале должно быть ноль строк specified multiple times. Пока я этого не заметил, замер мерил не ту раскладку, которую я задал.

--tensor-split не делит буфер экспертов. -ncmoe складывает всех снятых с процессора экспертов одним буфером на одну карту. Симптом выглядит как нехватка видеопамяти:

allocating 24649.75 MiB on device 1: cudaMalloc failed: out of memory

при том что вторая карта почти пустая. -ts 1,1 раскладку не меняет вообще. Балансировку даёт только -ot с явными правилами по слоям и устройствам.

Генерация и обработка промпта хотят разного числа потоков. -t задаёт потоки генерации, -tb — обработки промпта. Генерация упирается в память, ей выгодно меньше потоков: 32 обыграли 64 и 96 на всех замерах, на обеих нодах. Обработка промпта упирается в вычисления и хочет все ядра. Поставив только -t 32, легко обвалить промпт и не заметить этого — потому что у сервера две скорости, а смотрят обычно на одну.

mmap поверх NFS даёт 0.07 t/s. Обязательны --load-mode mlock в команде и LimitMEMLOCK=infinity в юните. Проверять не по наличию флага, а по факту:

grep VmLck /proc/<pid>/status     # должен показать объём модели

Если mlock не разрешён, сервер молча продолжит работать через mmap. В журнале будет строка failed to mlock ... Cannot allocate memory, но сервер не упадёт.

Урезание контекста само по себе скорости не даёт — 10.5 против 10.5 т/с. Но освобождает видеопамять, которую можно отдать экспертам, и вот это уже ускоряет.

У Qwen3.8-Flash-Next в шаблон чата зашит режим размышления xhigh. На слово «привет» модель уходит думать по максимуму. Проверяется через /apply-template:

<|im_start|>system
Reasoning effort is set to xhigh. Please think carefully through the task...

Если при этом стоит --reasoning-format deepseek (по умолчанию), мысли уезжают в отдельное поле reasoning_content, веб-интерфейс их не рисует — и выглядит это как зависший сервер. Лечение: --reasoning-format none оставляет мысли прямо в ответе. Уменьшить объём размышления можно --reasoning-effort или --reasoning-budget.

systemd

Портит обратные слэши в ExecStart:

Ignoring unknown escape sequences: "blk\.[0-7]\.ffn_.*_exps\.weight=CUDA0"

Лечение — вынести команду в обычный shell-скрипт и звать его из юнита. Тогда кавычки и слэши ведут себя предсказуемо.

StartLimitIntervalSec живёт в секции [Unit], не в [Service].

Свои скрипты

Не брать вертикальную черту разделителем полей, если в данных встречаются регулярки: там она означает «или». Разбор результатов через cut -d'|' обрезал правило -ot на первой же черте внутри самого правила — служба получила огрызок -ot blk\.(8 и упала с invalid value. Правило шире: разделитель не должен встречаться в данных.

Вахта обязана мерить прирост, а не снимок. «Служба active» не доказывает ничего — процесс может стоять. Считать дельту за интервал и поднимать тревогу на двух пустых подряд.

Сборка

nvcc может отсутствовать в PATH у systemd-службы, хотя в интерактивной оболочке он есть. Симптом: CMakeDetermineCUDACompiler ... No such file or directory. Лечение — искать компилятор явно и передавать -DCMAKE_CUDA_COMPILER.

Маски исключений в tar сопоставляются с каждым компонентом пути. --exclude='models' вырезал tools/mtmd/models/models.h, а --exclude='build-*' — cmake/build-info.cmake и common/build-info.cpp.in. Обе сборки упали. Исключать точным путём от корня архива: --exclude='llama.cpp/build'.

git fetch по короткому хешу не работает — couldn't find remote ref. Нужен полный сорокасимвольный хеш; получить его можно через api.github.com/repos/<owner>/<repo>/commits/<короткий>.

Диф PR с гитхаба ≠ то состояние, под которое написан патч. GitHub отдаёт диф текущей головы PR против её базы. Если патч писался под конкретный коммит — брать именно его, а не .diff.

HuggingFace

HF_HUB_DISABLE_XET=1 обязателен, иначе закачки виснут на нуле.

Размер репозитория не равен размеру модели. У Qwen3.8-Flash-Next кванты «под vLLM» весят 167–175 ГБ — больше, чем GGUF того же класса на 111 ГБ.

Замеры

Замер без записанной методики — не факт, а легенда. Цифра «113 t/s» из собственного ранбука не воспроизвелась именно потому, что методика не была записана рядом с ней.

Temperature 0.6 и 400 токенов дают разброс в 20 пунктов на одинаковых промптах. Нужен greedy, прогрев и повторы.

Полоса памяти в синтетике не предсказывает выход модели. Разница 3.17× по STREAM превратилась в 1.74× на живой генерации.

Первый запрос после старта всегда медленнее — это прогрев, а не конфигурация. Без прогрева легко записать в отчёт цифру вдвое ниже реальной.

Сборка ветки 0.2.x форка

Три стены подряд, каждая молчаливая. Без них ветка не собирается вовсе.

Патч в самом репозитории битый. build.sh останавливается с внятным сообщением: CUDA 13.0 requires toolchain-patches/cuda-13.0-glibc-2.41-rsqrt.patch on glibc 2.43. Но патч не накладывается: в первом куске объявлено 11 старых строк, а фактически их 10 — не хватает строки контекста. GNU patch читает заголовок следующего куска как содержимое и падает на строке 21 с malformed patch. Правки простые (8 замен в crt/math_functions.h и .hpp: __GNUC_PREREQ → __GLIBC_PREREQ, блок _NV_RSQRT_SPECIFIER и приписка спецификатора к четырём объявлениям rsqrt/rsqrtf), накладывать вручную с проверкой единственности каждого совпадения.

В контейнере CUDA не инициализируется при живом nvidia-smi. Симптом обманчивый: nvidia-smi показывает обе карты, torch.cuda.device_count() возвращает 2, а torch.cuda.is_available() даёт False с CUDA unknown error. Причина — не разрешён старший номер устройства /dev/nvidia-uvm, а именно через UVM CUDA и считает. Смотреть ls -l /dev/nvidia-uvm и добавлять в конфиг LXC:

lxc.cgroup2.devices.allow: c 504:* rwm

Номер может отличаться — он динамический. Списки разрешений копировать с рабочего контейнера, а не из общего шаблона: именно на этом я и попался.

Лаунчер 0.2.x демонизирует сервер и выходит. С Type=simple systemd считает службу завершённой сразу после успешного smoke-теста и убивает всю группу процессов — в журнале это выглядит как State 'stop-sigterm' timed out. Killing. после строчек Health check: OK и Smoke response: OK. Нужен Type=forking с PIDFile=run-logs/vllm-<SERVED_NAME>.pid. На ветке 0.1.x лаунчер оставался на переднем плане, поэтому там тот же юнит работал.

Готовые профили ветки — под nvfp4. Это формат для Blackwell; на Turing брать их не надо. Заводите свой, зеркалящий рабочий профиль со старой ветки, — тогда сравнение движков будет честным.

Подключение к Open WebUI

Сервер поднялся и отвечает на curl — а чат всё равно не работает. Три грабли подряд, все три встречаются сразу после первого успешного запуска.

vLLM отказывается отвечать на tool_choice: "auto":

"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set

Open WebUI подставляет это поле само, стоит включить в интерфейсе хоть один инструмент, — и тогда ошибку получает даже слово «привет». Лечение: два ключа, но в юнит службы, а не в профиль кванта. В лаунчере форка они перечислены в profile_key_is_global, то есть читаются из окружения и профилю не принадлежат; профиль стоит держать зеркалом рабочего, иначе сравнение движков между ветками перестаёт быть честным.

Environment=ENABLE_AUTO_TOOL_CHOICE=1
Environment=TOOL_CALL_PARSER=qwen3_xml

Парсер выбирается по шаблону чата самой модели, а не по её имени. Загляните в chat_template.jinja:

что в шаблоне парсер
есть <function= и <parameter= qwen3_xml
только <tool_call> с JSON внутри hermes

У Qwen3.8-27B-AWQ-MTP присутствуют оба тега — значит qwen3_xml. Проверка честности: ответ должен прийти с finish_reason: "tool_calls" и заполненным tool_calls, а не текстом, в котором модель «нарисовала» вызов словами.

Пустой ответ у думающей модели — это лимит токенов, а не поломка. С --reasoning-parser qwen3 рассуждения уезжают в отдельное поле reasoning, и при коротком max_tokens весь бюджет уходит туда, а content приходит null:

max_tokens=60   -> content: null,  reasoning: 406 символов
max_tokens=700  -> content: 233 символа, reasoning: 406, finish_reason: stop

Выглядит как сломанный сервер, лечится числом. Прежде чем чинить — посмотрите, что лежит в reasoning.

Open WebUI разлогинивает всех при каждом перезапуске контейнера. Если переменная WEBUI_SECRET_KEY пуста и файла .webui_secret_key в томе нет, ключ подписи сессий генерируется случайным при старте — все выданные токены становятся недействительными. Со стороны это выглядит как пропавшая учётная запись, хотя в базе целы и пользователи, и чаты. Лечение — положить постоянный ключ в том с данными, чтобы он пережил и перезапуск, и обновление образа:

D=/var/lib/docker/volumes/open-webui_open-webui-data/_data
head -c 32 /dev/urandom | base64 | tr -d '\n' > "$D/.webui_secret_key"
chmod 600 "$D/.webui_secret_key"

Мёртвое подключение тормозит весь список моделей. Open WebUI опрашивает все прописанные адреса при каждом обновлении списка; один выключенный сервер в списке даёт Connection error и задержку на каждом заходе. Выключенные адреса лучше отключать, а не оставлять «на потом».

Сервер падает на втором сообщении в чате

Симптом со стороны человека: первое сообщение получает ответ, второе — Open WebUI: Server Connection Error. В журнале сервера:

torch.AcceleratorError: CUDA error: an illegal memory access was encountered

Трассировка указывает на synchronize_input_prep — но она бесполезна, ошибки ядер CUDA всплывают асинхронно на постороннем вызове. Смотреть надо дамп планировщика чуть выше:

scheduled_cached_reqs = CachedRequestData(req_ids=[два id],
    num_computed_tokens=[565, 383], num_output_tokens=[208, 99])
total_num_scheduled_tokens = 10
scheduled_spec_decode_tokens = {id1: [-1,-1,-1,-1], id2: [-1,-1,-1,-1]}

Два запроса генерируют одновременно, десять токенов в батче — это 2 × (1 + 4 черновика MTP). Связка «батч больше единицы + спекулятивное декодирование + CUDA-граф» на Turing даёт обращение по чужому адресу.

Почему это не ловится замерами. Скрипт замера шлёт запросы строго по одному, поэтому батч из двух не проверяется вовсе. А Open WebUI параллельно с ответом отправляет свою фоновую задачу — генерацию заголовка чата. То есть реальная нагрузка чата всегда содержит хотя бы две последовательности, и первое же второе сообщение попадает ровно в этот путь.

Лечение — одна последовательность за раз:

MAX_NUM_SEQS=1

Держите это отдельным боевым профилем, не правя замерный: иначе сравнение веток движка перестаёт быть честным. Для одного человека в чате разницы не видно — запросы просто выстраиваются в очередь.

И поставьте перезапуск, ограниченный по частоте. С Restart=no упавший сервер лежит молча: у нас он умер в 05:17 и был обнаружен через три часа.

[Unit]
StartLimitIntervalSec=3600
StartLimitBurst=3
[Service]
Restart=on-failure
RestartSec=30

Проверка честности фикса — воспроизвести то, что убивало. «Служба active» не доказывает ничего; надо послать два запроса одновременно и посмотреть, что оба ответили, а в свежем журнале ноль строк illegal memory access.

Часы контейнера. Если контейнер живёт по UTC, а вы по местному времени, время падения в журнале разойдётся с моментом, когда человек нажал «отправить». Мы на этом чуть не построили ложный вывод: 05:17 в журнале оказалось ровно 08:17 на телефоне.

Интерфейс не показывает скорость в токенах

Две разные причины, и лечится только одна из них.

Счётчик пуст, потому что сервер не шлёт статистику. vLLM кладёт usage в поток только тому клиенту, который попросил через stream_options. Open WebUI её обрабатывает (normalize_usage в потоковом пути), но не запрашивает — строки include_usage в его бэкенде нет вовсе. Лечится на стороне сервера:

Environment=FORCE_INCLUDE_USAGE=1      # -> --enable-force-include-usage

Лаунчер форка про этот флаг не знает, строку надо добавить рядом с прочими:

[[ "${FORCE_INCLUDE_USAGE:-0}" == "1" ]] && VLLM_ARGS+=(--enable-force-include-usage)

Это правка файла форка — обновление её сотрёт. После каждого обновления: grep FORCE_INCLUDE_USAGE launcher.sh.

Проверка: послать потоковый запрос без stream_options и убедиться, что последний чанк содержит usage.

А вот скорости не будет всё равно, и обновление не поможет. Open WebUI вычисляет response_token/s единственной формулой — eval_count делить на eval_duration. Это поля Ollama; у OpenAI-совместимого сервера их нет. Проверено сверкой исходников 0.10.2 и 0.11.1: формула в обеих одна и та же и живёт внутри convert_ollama_usage_to_openai. То есть с vLLM интерфейс покажет количество токенов, но не скорость — независимо от версии.

Готовая сборка: четыре стены, все проверены на чистых машинах

Ставили готовые колёса на два свежих контейнера — Ubuntu 24.04 и 22.04, оба пустые, как у человека, который только что купил карты. Вот что встретилось.

Два колеса одной командой не ставятся

ERROR: Cannot install flash-qla==0.1.0+3ab27d7 and vllm==0.2.1rc3+cu130
       because these package versions have conflicting dependencies.
    vllm 0.2.1rc3+cu130 depends on tilelang==0.1.12
    flash-qla 0.1.0+3ab27d7 depends on tilelang==0.1.8

Жёсткий конфликт: два пакета прибиты к разным версиям одной библиотеки, и pip такое не решает. Ставить надо по очереди, второе — без разрешения зависимостей:

pip install ./vllm-*.whl
pip install --no-deps ./flash_qla-*.whl

Это не обход ради обхода: на рабочем стенде стоят версии из vllm (tilelang 0.1.12, apache-tvm-ffi 0.1.11), и flash_qla с ними работает — его пины просто устарели. Проверено на живом сервере, не рассуждением.

Почему мы этого долго не видели. Свои проверки мы делали с --no-deps для обоих колёс, и конфликт не всплывал. Он вылезает только при честной установке на чистую машину — то есть ровно у того, кто повторяет за нами.

На Ubuntu 22.04 первым падает Python, а не glibc

Мы писали «упирается в glibc 2.38». На деле стена другая и приходит раньше:

python3 -> Python 3.10.4
ERROR: vllm-...-cp312-cp312-linux_x86_64.whl is not a supported wheel on this platform.

Колёса собраны под cp312, в 22.04 системный питон 3.10, и pip отказывает сразу — до glibc дело не доходит вовсе. Стены две, и питоновая первая.

В LXC-контейнере проброса устройств недостаточно

Карты проброшены, /dev/nvidia0 на месте — а nvidia-smi говорит «команда не найдена». Драйвер состоит из двух частей, и они живут врозь:

  • модуль ядра — только на хосте;
  • библиотеки — внутри каждого контейнера.

Внутрь контейнера ставится тот же самый установщик той же версии, но без модуля:

./NVIDIA-Linux-x86_64-<версия>.run --no-kernel-module --silent

После этого nvidia-smi в контейнере показывает карты. Проверено: до — «команда не найдена», после — обе карты, 22528 MiB, sm_75.

Версия обязана совпадать с хостовой до последней цифры. А вот дистрибутив не важен: у нас хост Debian 13, контейнер Ubuntu 26.04, драйвер один.

Модель думает и не отвечает

Симптом: на любой вопрос приходит только размышление, ответа нет вовсе.

max_tokens=900   ответ 0 символов, рассуждение 3381
max_tokens=2000  ответ 0 символов, рассуждение 7527

Причина в шаблоне чата самой модели:

{%- set resolved_reasoning_effort = reasoning_effort|default('xhigh') %}

По умолчанию xhigh — модели велено на каждый вопрос «продумать тщательно, проверить допущения, рассмотреть альтернативы». Она честно это делает и упирается в лимит токенов раньше, чем доходит до ответа. Шаблон принимает три значения: xhigh, medium, low.

Environment='DEFAULT_CHAT_TEMPLATE_KWARGS={"reasoning_effort":"low"}'

Стало:

«17 × 23»           рассуждение  110 -> ответ сразу
быстрая сортировка  рассуждение  344 -> ответ 1615 символов
турбореактивный     рассуждение  863 -> ответ 2029 символов

Строки вида !!!!!!!!!!!! в ответе

Сервер запускается с --generation-config vllm, а это значит «настройки из самой модели игнорировать» — включая штраф за повтор. Любопытно, что сборка AWQ везёт repetition_penalty 1.05 в своём generation_config.json, а сборка INT8 не везёт вовсе; но при этом флаге не работает ни та, ни другая.

Задаётся явно, и при режиме vllm это единственный источник параметров:

Environment='OVERRIDE_GENERATION_CONFIG={"repetition_penalty":1.05}'

systemd снимает двойные кавычки в Environment

Оба ключа выше — JSON, и с первого раза они не заработали:

api_server.py: error: argument --default-chat-template-kwargs:
               invalid loads value: '{reasoning_effort:medium}'

Кавычки исчезли по дороге. Лечение — взять всё присваивание целиком в одинарные кавычки, как в примерах выше. Это тот же класс, что и с обратными слэшами в ExecStart.
